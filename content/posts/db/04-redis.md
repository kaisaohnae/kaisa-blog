# Redis: 인메모리 키-값으로 캐시·세션·큐

> 요약: 캐시, 세션, 레이트 리밋, 단순 큐까지 Redis를 쓰는 패턴과 영속성·만료·실수 포인트를 정리한다.

---

## 1. 언제 Redis인가

| 용도 | 예 |
|------|-----|
| 캐시 | API 응답, 핫 키 |
| 세션 | 로그인 세션 스토어 |
| 카운터·레이트리밋 | `INCR` + TTL |
| 단순 큐/스트림 | 리스트, Streams |
| 분산 락 | 신중히 (레드락 등) |

주 데이터베이스를 대체하기보다 **빠르고 휘발·만료가 자연스러운 계층**으로 둔다.

---

## 2. 자료구조

| 타입 | 용도 |
|------|------|
| String | 캐시 값, 카운터 |
| Hash | 객체 필드 |
| List | 단순 큐 |
| Set / ZSet | 태그, 랭킹 |
| Stream | 메시지 로그 |

```bash
SET user:42:profile '{"name":"Ada"}' EX 3600
INCR ratelimit:42:2026082615
EXPIRE ratelimit:42:2026082615 60
```

---

## 3. 만료·메모리

- TTL을 기본으로 설계
- maxmemory + eviction 정책(`allkeys-lru` 등)
- 큰 키·무제한 컬렉션(무제한 List) 주의
- 핫 키 한곳에 몰리면 스케일 전에 병목

---

## 4. 영속성·운영

- AOF / RDB는 **유실 허용 범위**에 맞게
- 캐시 전용이면 재시작 유실을 전제로 앱이 동작해야 한다
- 비밀번호·보호 모드·VPC 내부 노출
- 클러스터/센티널은 필요 시

---

## 정리

Redis는 DB라기보다 **저지연 데이터 구조 서버**다. TTL·메모리·유실 허용을 먼저 합의한다.
